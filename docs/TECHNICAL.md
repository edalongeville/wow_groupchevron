# GroupChevron: implementation notes

Details for contributors. User-facing documentation is in the [README](../README.md). The version in parentheses is the addon version that introduced or last changed the item.

- **Friendly NPCs (0.23.0):** a friendly NPC (`Core.FriendlyNPC`: `UnitIsPlayer` false, `UnitIsFriend` true, `UnitCanAttack` false, exact booleans) gets mode **npc** (`Core.PlateMode`, checked after **quest** and before any relation) whenever the addon has something to do on it (`Core.NpcPlate`): a role icon (`Core.ServiceNPC`: `npcicons` on, default, and a known role), compact plates (`npccompact`, default on) or a name size other than 1 (`npcsize`, 1 to 3, default 1); with all three off the plate stays Blizzard's. The look (`NpcStyle`, `keepcolor`): Blizzard's name colour is kept and our name is drawn at `npcsize` (`Mark` leaves Blizzard's name alone when the colour cannot be read); with `npccompact` the plate is name only (`Compact`, health bar while hurt, never scaled: its `bar` argument), except on the target, which keeps its full plate. The role (`Core.ROLES`, in priority order: flight, innkeeper, banker, auctioneer, stable, trainer, repair, vendor; an NPC with two roles shows the first) is asked by `Core.UnitInfo` only with `npcicons` on, and is the better (`Core.BetterRole`) of two sources (`Core.ServiceLookup`): the role **learned** for its creature ID (`Core.NpcID` of `UnitGUID`: `Creature-` / `Vehicle-` GUIDs only), and the role its **subtitle** gives (`Core.TooltipSubtitle`: the second line of `C_TooltipInfo.GetUnit(unit)`; `Core.SubtitleRole` matches lower-case words of `Core.SUBTITLES` for `GetLocale()`: enUS/enGB and frFR only; of the French words only "Maître des gryphons", the Forever client's spelling, is checked in game; other clients rely on learned roles). Roles are learned (`LearnFromNPC`, only while the addon and `npcicons` are on) from the windows an NPC opens: `MERCHANT_SHOW` (`repair` when `CanMerchantRepair()` is true, else `vendor`), `TAXIMAP_OPENED`, `BANKFRAME_OPENED`, `AUCTION_HOUSE_SHOW`, `TRAINER_SHOW`, `PET_STABLE_SHOW`, `CONFIRM_BINDER`, and `PLAYER_INTERACTION_MANAGER_FRAME_SHOW` for the matching `Enum.PlayerInteractionType` names (`Core.InteractionRole`); the creature ID is read from the `npc` unit, whose identity is not secret during an interaction (12.0.7 API notes). They are saved in `GroupChevronDB.npcroles` (creature ID -> role key, cleaned by `Core.CleanRoles`; `Core.LearnRole` only upgrades a role) and trigger the coalesced `RefreshAll`. The icon (`Core.RoleIcon`: 64 x 64 `Interface\Icons` spell and item icons, their bevelled border cropped by `Core.ICON_CROP`; the minimap tracking icons of the first build were too low-res once enlarged; the names are the retail client's, unverified on the Forever client: a texture that does not load shows no icon and says so once) can be changed per role (`/gchev icon <role> <name>`, saved in `db.roleicons`, cleaned by `Core.CleanRoleIcons`; a name with a `\\` or `/` is a texture path, cropped only under `Interface\\Icons` (`Core.IconCrop`), anything else an atlas, refused when `C_Texture.GetAtlasInfo` does not know it, set with `SetAtlas`), and sits `GAP` above the name, `6 x npciconsize` UI units square (1 to 15, default 5), in its own frame (`icons`, keyed by `UnitFrame`, hidden by `Unmark` and by `Mark` for any style without an icon, kept by compact mode). The game's friendly NPC plates setting (`nameplateShowFriendlyNPCs`, unverified on the Forever client) is only changed on request: `/gchev npcplates on|off` and the first checkbox of the **Friendly NPCs** section (`SetNpcPlates`: refused in combat, on a client without the CVar, or when the client does not take the value); `PLAYER_ENTERING_WORLD` says once per install (`db.npcplatesnoticed`) that they are off. Out of combat only, in practice: a secret GUID or tooltip means no role, so the icon goes until the next refresh out of combat. `/gchev` and `/gchev debug` print the role, its source and the subtitle read. Not verified in game yet (only the "Maître des gryphons" spelling was seen, above the NPC).
- **Why a name stays Blizzard's (0.22.1):** a marked plate (member, friend, guildmate, class colour, quest hostile) is coloured and chevroned on Blizzard's name, but only drawn at `textsize` / `othersize` / `hostilesize` by our own FontString when `ShowFullName` can draw it. When it cannot, the plate shows Blizzard's name in our colour at Blizzard's size (seen in game: two members side by side, one at `textsize`, one much smaller). `ShowFullName` now records why, per `UnitFrame` (`nameFails`): `name text unreadable (secret or empty)`, `name font unreadable`, `no CreateFrame` or `Blizzard's name hidden` (`IsShown() == false` when the mode was applied). `/gchev names` lists every marked plate whose name is not ours, with the reason, and counts them ("N marked at Blizzard's size"); `/gchev debug` on the target prints the reason and the raw name text (`secret` for a secret value). Diagnostic only: no behaviour changed.
- **Hostiles tied to a quest (0.21.0):** a hostile unit tied to one of the player's active quests gets mode **quest** (`Core.PlateMode`, checked before any relation): our own name in the hostile colour (`hostilecolor`, default `#FFFF00`) and a **single** chevron in the same colour above it; the rest of its plate (health bar, cast bar, auras) stays Blizzard's, and compact mode never applies. A unit counts when `UnitCanAttack("player", unit)` is true (hostile and neutral units alike: kill targets are often neutral) and `C_QuestLog.UnitIsRelatedToActiveQuest(unit)` is exactly `true` (`Core.UnitInfo` reads `attackable`, `quest`, `questSource`; `Core.QuestLookup`, `Core.QuestHostile`). The quest API is only asked for a unit known to be attackable. It is a boolean, documented for retail 10.0.0 and for the Forever client 1.60.1 (`AllowedWhenUntainted` only concerns secret *arguments*; we pass a plain `nameplateN` token), and covers every kind of link the client knows (kill, item drop, interact), so there is no per-objective logic of ours. A missing API, an error or a secret value means "not tied to a quest": the plate keeps Blizzard's look. The single chevron is the upper "V" of the double one (same `chevron.tga`, fully opaque, 10 x 5 at size 1, frame cached apart from the double chevron in `singles`; a pooled `UnitFrame` may show either shape in turn, the other one is hidden). Its four settings mirror the friendlies': `hostilecolor` (name and chevron), `hostilechevsize` (1 to 5, default 3 like `chevsize`, which the friends' chevron uses), `hostilesize` (name, 1 to 3, default 1 like `othersize`) and `hostilenamegap` (whole points, -10 to 40, default 5 like `othernamegap`), also in the **Quest hostiles** group of the settings page (created after the other groups and before the font control) and as `/gchev hostilecolor|hostilechevsize|hostilesize|hostilenamegap`; **Reset to defaults** resets them. The plates are re-checked (one coalesced `RefreshAll`, like the friend list) on `QUEST_LOG_UPDATE`, `UNIT_QUEST_LOG_CHANGED`, `QUEST_ACCEPTED` and `QUEST_REMOVED`. `/gchev` and `/gchev debug` print whether the target counts, with the API that answered and `attackable`. Not verified in game yet: check with `/gchev debug` on a quest mob (and a mob that is not), that `UnitIsRelatedToActiveQuest` answers `true` for kill and drop objectives and `false` once the objective is complete, and that Blizzard's enemy plates show a name (the `UnitNameHostleNPC` CVar) so that the yellow name is visible; without it only the chevron shows.
- **Chevron sizes per section (0.21.0):** the chevrons of the friends and of the guildmates have their own size settings, `friendchevsize` and `guildchevsize` (1 to 5, default 3, like `chevsize`, which is now the group members' only; `/gchev friendchevsize|guildchevsize 1-5`; a slider in each section). `LayoutChevron(frame, thickness, sizeKind)` takes the size kind from `style.chevsize`. A `chevsize` saved by an earlier version no longer applies to friends and guildmates.
- **Chevron outline and previews (0.21.0):** each "V" of a chevron frame also has eight black copies of itself (same `chevron.tga`, same alpha, below it, `owner` = the "V"), each moved by the thickness in one of eight directions (`OUTLINE_DIRS`): `OUTLINE_UNIT` (0.1875) x the section's thickness factor x the chevron size, so the outline grows with the chevron. Thickness factors `memberoutlinesize`, `friendoutlinesize`, `guildoutlinesize`, `hostileoutlinesize`: 0 to 5, default 2 (`Core.MIN_FACTORS`, `Core.MAX_FACTORS`, `Core.DEFAULT_FACTORS`; slider and `/gchev <name> 0-5`); 0 hides the copies (there is no separate on/off setting; `style.outlinesize`); `LayoutChevron(frame, thickness)` re-lays the frame out when the chevron size or the thickness changes. Reset to defaults restores all eight. The settings page draws a preview of the chevron (plain textures of the content frame, at the plates' size (chevron size slider, 1 to 5 points per unit), single V for hostiles) in a grey rounded square (`backdrop.tga`, tinted at runtime, generated by `tools/preview_backdrop_tga.py`; a plain square if the texture cannot load) to the right of the colour and outline rows of each of the four sections, recoloured and re-outlined by `RefreshPanel`; each section has an **Outline** slider right below the colour swatch, and dragging it, or the chevron size slider, redraws that section's preview before the value is saved.
- **Friends (0.8.0):** a relation layer on top of the modes, in priority order group member > friend > guildmate > class colour. A friend is a friendly player (`UnitIsPlayer`, `UnitIsFriend("player", unit)`, not you, known not to be a group member) whose `UnitGUID` is on the character friends list (`C_FriendList.IsFriend(guid)`) or, with `bnetfriends` on, a Battle.net friend's character (`C_BattleNet.GetAccountInfoByGUID(guid).isFriend == true`; not even asked with the setting off) (`Core.FriendLookup`, `Core.Relation`; none of these APIs is verified on the Forever client: a missing function, an error or a secret value means "not a friend", and the plate keeps the look it has without this layer). `Core.PlateMode` returns the mode and the relation: a friend who is your target, or any friend with compact off, gets mode **friend** (Blizzard's full plate, our own name in the friend colour, the chevron when `friendchevron` is on; since 0.17.1 the name and the health bar use `othersize` / `otherbarsize` when compact is off, and since 0.17.2 also for your target with compact on; the member sizes never apply); a non-target friend with compact on stays a **compact** plate (name only, health bar while hurt, `othersize` / `otherbarsize`), now in the friend colour and with the chevron. The chevron is the member one (same texture, geometry, `chevsize`) tinted with the friend colour. The record of Blizzard's colour is kept across member ↔ friend changes (`marks`, keyed by `UnitFrame`), so leaving every marked mode (unfriended, target change, recycling, removal, settings change, `/gchev off`) gives Blizzard's colour and alpha back. The visible plates are re-checked on `FRIENDLIST_UPDATE`, `BN_FRIEND_LIST_SIZE_CHANGED`, `BN_FRIEND_INFO_CHANGED` and `BN_FRIEND_ACCOUNT_ONLINE` / `OFFLINE` (each registered under `pcall`, an unknown event is skipped), coalesced into one `RefreshAll` per burst 0.2 s later (`C_Timer.After`; without it, at once). Not verified in game yet: check with `/gchev debug` on a friend.
- **Guildmates (0.11.0):** the next relation after friend: priority group member > friend > guildmate (a friend who is also a guildmate is shown as a friend). A guildmate is a friendly player (same conditions as a friend, but not on the friends list) for whom `Core.GuildLookup` says yes: only when `IsInGuild()` is true (otherwise no guild API is called), `UnitIsInMyGuild(unit)`, and only when that function does not exist, `IsPlayerInGuildFromGUID(UnitGUID(unit))` (global, else `C_PlayerInfo`). A missing function, an error or a secret value means "not a guildmate" (none of these is verified on the Forever client). `Core.PlateMode` treats the `guild` relation like `friend` (target keeps the mark with the full plate; compact on/off as for friends), in `guildcolor` with the chevron when `guildchevron` is on. The plates are re-checked on `PLAYER_GUILD_UPDATE` and `GUILD_ROSTER_UPDATE`, coalesced with the friend list events into one `RefreshAll` per burst. `/gchev debug` (and `/gchev`) print whether the target counts as a guildmate and which API answered.
- **Sizes on full plates (0.17.1):** `othersize` and `otherbarsize` now also apply to the full plates of friends, guildmates and class-coloured friendly players when compact is off (name and health bar). They used to apply only to compact plates, so with compact off these plates stayed at size 1. Your target with compact on keeps size 1, group members keep `textsize` / `barsize`, and the default of 1 changes nothing.
- **Sizes on the target (0.17.2):** `othersize` and `otherbarsize` apply to every friendly player outside the group (`Core.OtherSizes`: friendly, not a member, not you; compact and the target state do not matter), so their name and health bar no longer jump back to size 1 when you target them with compact on. This also covers a plain friendly (no friend, guildmate or class colour) on a full plate, compact on (the target) or off: the addon draws its name in Blizzard's colour at `othersize` when the level follows it or `othersize` is not 1 (else Blizzard's name stays), and scales its health bar to `otherbarsize` when it is not 1. Any other default plate (enemies, NPCs) gets its original scales back, so a pooled `UnitFrame` never keeps a friendly's bar size. Not verified in game yet.
- **Name height (0.18.0):** `/gchev namegap <-10..40>` (group members) and `/gchev othernamegap <-10..40>` (every friendly player outside the group, wherever `othersize` applies: compact plates and full plates, the target included) move the addon's own name label up (positive) or down (negative) from where Blizzard puts its name above the health bar, in whole UI points (not scaled by the text size), default `0` = the layout as before. Also a "Name height" slider in the **Group members** and **Friendlies** groups of the settings page (step 1, applied on release), reset to 0 by **Reset to defaults**. Saved as `GroupChevronDB.namegap` / `othernamegap` (a whole number in -10..40; missing or invalid = 0; decimals and out-of-range values are refused with a message, no clamping, `Core.ValidGap` / `ParseGap` / `SnapGap`). The anchor offset is `(buff lift + gap) / text size` (`Core.NameOffset`), so for members it adds to the `buffsize` lift, and the chevron, anchored on the name, moves with it. Only the addon's own name moves: on a plain friendly's full plate with level off and `othersize` 1, a non-zero `othernamegap` makes the addon draw the name (in Blizzard's colour) so it can move; where the addon's name cannot be drawn (unreadable text or font) Blizzard's name stays where it is. Not verified in game yet, in particular with enlarged bars and buffs.
- **New defaults (0.20.0):** a fresh install (or a value missing or invalid in `GroupChevronDB`) now starts with the look the author plays with: font `outline` (System (outline)), `chevsize` 3, `textsize` 1.75, `buffsize` 1.1, `namegap` and `othernamegap` 5, and `classcolor` on; `barsize`, `othersize` and `otherbarsize` stay 1, and the colours and the other flags are unchanged. The defaults live in `Core` (`DEFAULT_FACTORS` / `DefaultFactor(kind)`, `DEFAULT_GAP` / `DefaultGap(kind)`, `DEFAULT_FONT`, `DEFAULT_CLASSCOLOR`) and are used by `InitDB`, the fallbacks of the plate code, **Reset to defaults** and the slash command help. `Core.DEFAULT_FACTOR` (1) and `Core.NO_GAP` (0) stay the neutral values the plate code compares against to know that nothing is scaled or moved. Settings a player already saved are valid values and are kept as they are; only values never saved get the new defaults. In the specs, `load()` starts from neutral settings (size 1, no gap, Blizzard's font, class colour off) unless a spec passes `factory = true`, so the behaviour specs do not depend on the defaults.
- **Localisation (0.15.0, every client locale since 0.22.0):** the settings page texts (group titles, labels, checkboxes, sliders, Reset button) come from `Core.Locales` by `GetLocale()`. Every locale the game client can report has texts (`Core.CLIENT_LOCALES`): `enUS`, `frFR`, `deDE`, `esES`, `itIT`, `ptBR`, `ruRU`, `koKR`, `zhCN`, `zhTW`, plus `enGB` (English) and `esMX` (shares `esES`); ptPT clients report `ptBR`. An unknown locale, or a key missing from the locale, shows the English text (`Core.Translate`, never an error); a spec checks that every client locale defines exactly the English keys. The `.toc` has a `## Notes-<locale>` line for each (the AddOns list description). The addon name, the font names, chat output and `/gchev` help stay English. Where a language has no common word for "chevron", Chinese uses "V形标记" / "V形標記" and Korean "표식" (marker). None of the translations (French included) is reviewed by a native speaker or checked in game for overlaps; labels were kept short for the fixed-width spots (Outline about 70 px, Name font about 80 px, Show level about 120 px).
- **Name font (0.14.0):** `/gchev font default|outline|chat|large|game13` (also a drop-down on the settings page listing them, or a button that cycles through them if the client has no `UIDropDownMenu` API; saved as `GroupChevronDB.font`, invalid = `default`) picks the font of the addon's own name labels from client font objects (`Core.FONTS`: `SystemFont_Outline`, `ChatFontNormal`, `GameFontNormalLarge`, `Game13Font_o1`), for readability on bright terrain. `default` keeps Blizzard's own name font as before. Font objects rather than file paths keep the client's Cyrillic/Korean/Chinese fallbacks; a missing global falls back to `default`. It only applies to our FontString (`SetFontObject`), never to Blizzard's name. Not verified in game yet: check the object names exist on the Forever client.
- **Chevron size up to 5 (0.9.0):** `chevsize` alone goes from 1 to 5; every other factor (`textsize`, `barsize`, `buffsize`, `othersize`, `otherbarsize`) stays 1 to 3. `Core.MaxFactor(kind)` gives the per-kind maximum used by validation, parsing, snapping, `InitDB`, the slider range and the slash command help/error text. A saved `chevsize` already in 1..3 is kept; above 5 it is reset to the default, same as any other out-of-range value.
- **Class colour (0.10.0):** with `classcolor` on, a friendly player who is neither a group member, a friend, a guildmate nor you gets their name in their class colour, whether compact is on or off and also as your target. The colour of a plate's name comes from `Core.NameColor` (pure, tested), in priority order member > friend > guild > class colour > Blizzard's colour, so members, friends and guildmates keep their own colour. The class token is the second result of `UnitClass(unit)` (e.g. `MAGE`) and the colour the client's own: `C_ClassColor.GetClassColor(token):GetRGB()`, else `RAID_CLASS_COLORS[token]` (`.r/.g/.b`), never a table of ours (`Core.ClassColor`; asked only with the setting on). A missing function, an error, a secret value or an unknown token gives no class colour: the name keeps the look it has without the setting. Modes: a non-target friendly with compact on stays a **compact** plate, its name in the class colour (at `othersize`); the target, or any friendly with compact off, gets mode **class**: Blizzard's full plate with only the name drawn by the addon's own FontString in the class colour (no chevron; since 0.17.1 the name and the health bar use `othersize` / `otherbarsize` when compact is off, and since 0.17.2 also for your target with compact on). Both reuse the friend path (`Mark`, records keyed by `UnitFrame`), so turning the setting off, leaving the mode, recycling or removal gives Blizzard's name, colour and alpha back as before. None of these APIs is verified on the Forever client: check with `/gchev debug` on a friendly player.
- **Level (0.12.0):** with `showlevel` on (default), a friendly player who is not a group member and not you (`Core.ShowsLevel`: friends, guildmates and class-coloured friendlies included, compact on or off, your target too) shows `<name> (<level>)` (`Core.NameWithLevel`): `UnitLevel(unit)` of 1 or more as is, `-1` or less (unknown to the client) as `(??)`; a level that is not readable (missing function, error, secret value, non-integer, 0) gives the name alone (`Core.UnitLevel`). The level is part of the addon's own name text (see Full name below), so it has the name's colour (member, friend, guild, class or Blizzard's), size (`othersize` on compact plates and, since 0.17.1, on the full plates of friends, guildmates and class-coloured players with compact off; since 0.17.2 on every friendly non-member's full plate, your target included) and font object; Blizzard's name text is never changed. On a full non-member, non-friend, non-guild, non-class plate (compact off, or the target), the name is drawn by the addon's own FontString only while a level is shown or `othersize` is not 1 (Blizzard's colour, `othersize`; the rest of the plate stays Blizzard's but the health bar, at `otherbarsize`), and Blizzard's name gets its alpha back otherwise. Our name stays centred on Blizzard's, and the chevron stays anchored on its top. Refreshed by the name-update hook and by `UNIT_LEVEL` for a nameplate unit (registered under `pcall`). Not verified in game yet. **Only while the bar is hidden (0.19.0):** Blizzard's health bar shows the level beside it, so the suffix is now left out wherever that bar is visible. Full plates (compact off, your target, friends', guildmates' and class-coloured full plates) never get it: on a plain friendly's full plate the addon's own name is then drawn only when `othersize` or `othernamegap` is not the default. A compact plate gets it only while its health bar is hidden (full health), the same `/gchev level` setting: `Core.LevelSuffix` decides. With the health curve (secret health), the bar's state cannot be read, so the addon draws two labels of the same look on the same spot, the name with the level and the name alone (`rec.short`, created only for a level), and the client drives them: the name alone gets the bar's alpha, the name with the level that of the opposite curve (`Core.FULL_HEALTH_CURVE_POINTS`: 0 below full health, 1 at full health, built once, only when needed), both re-applied on every `UNIT_HEALTH` / `UNIT_MAXHEALTH`, never read or compared. Without the curve the readable-health fallback picks the text (`hurt`: name alone). In doubt the suffix stays: the curve failing, the bar refusing the secret alpha (name only), a label refusing it, or no health bar part. Blizzard's name handling (`SyncName`, `fadedNames`) is unchanged. Not verified in game yet: check that a compact friendly's suffix goes when hurt and comes back once healed.
- **Compact mode:** each visible plate gets a mode from `Core.PlateMode` (pure, tested), fed by `Core.UnitInfo`: **member** (group member: full plate, pink name, chevron), **compact** (a player, not you, `UnitIsFriend("player", unit)`, not a group member, not your target (`UnitIsUnit(unit, "target")`), compact on: name only) or **default** (everything else, including the addon off, compact off and any API error, missing function or secret value: the plate exactly as the game draws it; an unknown group membership never gives compact). There is no per-plate "name only" setter, so compact fades out, with `SetAlpha(0)`, everything in `UnitFrame`'s tree but the name: for the name FontString and each of its ancestors up to `UnitFrame` (`GetParent()`), the ancestor's other child frames and regions (`GetChildren()`, `GetRegions()`); no fixed list of field names. While the unit is hurt, `UnitFrame.HealthBarsContainer` and `UnitFrame.healthBar` are shown too. **Secret health (0.16.0):** on the Forever client `UnitHealth`, `UnitHealthMax` and `UnitHealthPercent` are secret values, which Lua cannot compare or test, so the bar's alpha is computed by the client: a colour curve built once (`Core.HealthCurve`: `C_CurveUtil.CreateColorCurve()` with `CreateColor`, white, alpha 1 at 0 and 0.999 of full health, 0 at full health) is evaluated by `UnitHealthPercent(unit, false, curve)` (`Core.HealthAlpha`), and the 4th value of the colour's `GetRGBA()` (secret) is passed straight to the health bar parts' `SetAlpha` under `pcall`, never read, compared or stored as a key (checked in game on the targeted plate's `HealthBarsContainer`; a frame that refuses a secret alpha gets `SetAlpha(0)`, name only). Because the alpha cannot be compared, `UNIT_HEALTH` / `UNIT_MAXHEALTH` re-apply it on every event, and the parts' `OnShow` hook re-applies it too. Without that API, or when it fails, the readable-health fallback of up to 0.15.0 applies (`Core.HealthMissing`: `UnitHealth < UnitHealthMax`, both readable; an error or a secret value counts as full health, so the plate stays name-only): `UNIT_HEALTH` / `UNIT_MAXHEALTH` re-check a compact plate only when its unit crosses "full" either way. Either way a part no longer to fade gets its alpha back at once. `/gchev debug` prints the target's `UnitHealth`, `UnitHealthMax` and `UnitHealthPercent` (`secret` instead of a secret value), whether the curve works, and the shown state and alpha of its health bar parts. It never hides or moves the plate, `UnitFrame`, the name or its ancestors (clicks and stacking keep working), nor the addon's own chevron. What it faded is recorded per `UnitFrame` (not per plate: since 0.6.2, see below) in weak-keyed tables and given alpha 1 back as soon as the plate leaves compact mode (member, target, another unit after recycling, removal, `compact off`, `/gchev off`). Each faded frame gets one `OnShow` hook (never two) that fades it again only while its plate is still compact (e.g. the cast bar), and parts that appear later are caught on the next name update. The mode is re-checked in the `CompactUnitFrame_UpdateName` hook and on `NAME_PLATE_UNIT_ADDED`, `GROUP_ROSTER_UPDATE` and `PLAYER_TARGET_CHANGED` (the old and the new target both change). Forbidden plates (friendly plates in dungeons and raids) are skipped silently. Not verified in game yet. **UnitFrame pooling (0.6.2):** Blizzard pools the `UnitFrame`s apart from the plates (`NamePlateBaseMixin:AcquireUnitFrame` on `NAME_PLATE_UNIT_ADDED`, `ReleaseUnitFrame` on removal), so the `UnitFrame` a plate shows changes each time the plate is reused. Everything the addon changes lives on the `UnitFrame` (faded name and parts, scales, bar layout, and its own name and chevron frames, created as children of it), so every record is keyed by the `UnitFrame`, and the `CompactUnitFrame_UpdateName` hook also unmarks a `UnitFrame` that now shows a default plate (an enemy, say), while `RefreshAll` cleans every `UnitFrame` no plate shows. That was not enough (0.7.1): the `NAME_PLATE_UNIT_ADDED` / `REMOVED` handlers may run before or after Blizzard's (at removal the plate may already have given its `UnitFrame` back; at addition it may not have one yet), and Blizzard does not call `CompactUnitFrame_UpdateName` when it gives a `UnitFrame` a unit (`CompactUnitFrame_UpdateAll` skips it), so a `UnitFrame` could still reach an enemy with Blizzard's name faded (`alpha 0`, seen in game). GroupChevron now post-hooks Blizzard's nameplate driver (`NamePlateDriverFrame`, when it has these methods): `ReleaseUnitFrame(base)` undoes everything on `base.UnitFrame` before it goes back to the pool, and `OnNamePlateAdded(token)` applies the plate's mode once it has its `UnitFrame` and unit; the event handlers stay as a fallback. Up to 0.6.1 the records were keyed by plate: a `UnitFrame` could come back from the pool under another plate with Blizzard's name still faded (enemies without a name), and a plate's own name was drawn inside the first `UnitFrame` it ever had (invisible once that one was back in the pool). **Names given back (0.12.1):** the same symptom came back on 0.12.0, this time on the *target's* plate, which every target change refreshes, so not a missed moment: the record of the fade was wrong. Up to 0.12.0 the alpha to give back was read with `GetAlpha` when the name was faded, and the record was dropped whatever the `SetAlpha` that gave it back did (errors are swallowed); one fade not given back was then read as "originally 0" and given back as 0 on every later unit of that `UnitFrame`. Now Blizzard's name is always given alpha 1 (Blizzard's nameplate code never sets the name's alpha: Blizzard_NamePlates and CompactUnitFrame, 12.1.5 UI source), every name we faded is remembered (`fadedNames`) until a `SetAlpha(1)` is known to have worked (else chat says so once, and it is retried by every `RefreshAll` and on `PLAYER_REGEN_ENABLED`), and every refresh of a plate ends with `SyncName`, which gives Blizzard's name alpha 1 unless the addon's own name covers it right now, even when applying the mode raised an error. `spec/groupchevron_spec.lua` also runs a model of Blizzard's driver (pooling, either event order, combat with failing `SetAlpha(1)`) and checks after every step that each plate shows a name.
- **How:** it listens to `NAME_PLATE_UNIT_ADDED` / `REMOVED`, `GROUP_ROSTER_UPDATE`, `PLAYER_TARGET_CHANGED`, `PLAYER_ENTERING_WORLD`, `ADDON_LOADED` and the friend list events above. A unit is a member when `UnitIsPlayer`, not `UnitIsUnit(unit, "player")`, and `UnitInParty` or `UnitInRaid` (`Core.IsGroupMember`; an error or a secret value counts as "no"). The name FontString is `UnitFrame.name`, else `.Name`, else `.unitName` (unverified on the Forever client; without one, only the chevron is drawn, anchored to the top of `UnitFrame`, and chat says so once). Blizzard recolours names on its own updates, so the colour is re-applied from a `hooksecurefunc` on `CompactUnitFrame_UpdateName` (nameplate frames of group members only). The chevron is a child of `plate.UnitFrame` (it fades and hides with the plate), drawn from two copies of `GroupChevron/chevron.tga` (64 × 32, one white anti-aliased "V" with alpha, coloured with `SetVertexColor`, pixel snapping off so it scales smoothly with `chevsize`), created once per plate and cached in a weak-keyed table; if the client cannot load the texture (e.g. the addon was updated while the game ran: new files need a restart), chat says so once and four rotated `SetColorTexture` rectangles are drawn instead. The texture is generated by `tools/chevron_tga.py` (`python3 tools/chevron_tga.py GroupChevron/chevron.tga` from the repository root). **Full name:** Blizzard's name FontString is as wide as the health bar, so long or enlarged names end in "…". On the plates the addon handles (members, friends, compact non-members and friendly players in their class colour), the name is drawn by the addon's own FontString (a child frame of `UnitFrame`, kept visible by compact mode), anchored on the bottom centre of Blizzard's name, without a width limit, with Blizzard's font object (`SetFontObject(name:GetFontObject())`, so the same alphabet fallbacks: Cyrillic, Korean and Chinese names render; `GetFont` values only when there is no font object; `textsize` is the scale of its frame, never a `SetFont` size), shadow and text (copied on every name update), in pink for members and Blizzard's colour otherwise; Blizzard's name is faded with `SetAlpha(0)` and gets its alpha back when the plate leaves those modes. A name text that cannot be read (error or secret value) or a hidden name leaves Blizzard's name as it was (truncated, but never missing). The addon never calls `SetFont` on Blizzard's name: up to 0.4.0 it did for `textsize`, which replaced the name's font object by a single font file without Cyrillic glyphs, so Russian names showed as boxes, also on recycled plates until the next reload. Plates are recycled: a plate that stops showing a member loses its chevron and gets back the colour it had before. The geometry constants are at the top of `GroupChevron.lua`. Not verified in game yet.
- **AddOns-list icon:** `GroupChevron.toc` has `## IconTexture: Interface\AddOns\GroupChevron\icon` (no extension) and `GroupChevron/icon.tga` is the pink (`#FF4FD8`) double chevron, 64×64, 32-bit TGA with alpha, second stroke faded, on a transparent background. Unlike `chevron.tga` (white, tinted at runtime with `SetVertexColor`) it is pre-coloured, because the AddOns list cannot tint it. Regenerate from the repository root with `python3 tools/groupchevron_icon_tga.py GroupChevron/icon.tga` (same V geometry as `chevron_tga.py`). Whether the WoW: Forever client reads `IconTexture` is not verified in game; if not, the field is ignored.
